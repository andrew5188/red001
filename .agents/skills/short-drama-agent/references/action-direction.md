# 场景类型、武戏LoRA与动作Prompt

## 配置与开关

每场在project.json的scenes[]记录scene_type（drama/action/mixed）、performance_plan和action_lora（enabled、model、strength）。片段可覆盖；同一主工作流切换，不为文戏/武戏复制模板。优先级为片段显式值→场景值→项目默认。情绪、是否武戏和LoRA开关是不同设置，不能把开启LoRA等同于已写动作。

文戏默认关闭动作LoRA。武戏在存在可核对的H3动作LoRA时配置启用；模型未知、不兼容或用户关闭时不强行开启。用户显式开关优先，混合场景按片段区分。使用已有惰性开关，关闭分支真正旁路；保留原加速LoRA，动作LoRA作为另一个可选模型补丁，初期一次只选一种。模型/强度写入实际API和运行快照，不把界面显示当作已生效证据。

核对模型训练基座、适用输入模式、推荐强度和触发词，信息不足时标待试片；不得仅凭文件名宣称效果已验证。不将Wan/SD等其他基座的动作LoRA用于H3。缺少触发词来源时不猜造。读取文件头不代表与当前量化、加速LoRA和分块路径组合已通过渲染测试。

## 公共自然肤质LoRA与自动构建工作流

用户已指定文戏、武戏均默认使用自然肤质（去油腻）LoRA，独立于动作LoRA。使用appearance_lora（enabled/model/strength/trigger/sha256/source/validation）记录，覆盖优先级为片段→场景→项目；默认开启，用户显式关闭优先。当前默认候选为fal/MiniMax-H3-Realism-People-LoRA，文件h3-realism-people-t2v-i2v-r2v.safetensors、触发词r34l1sm、较轻起始强度0.6。作者模型卡：https://huggingface.co/fal/MiniMax-H3-Realism-People-LoRA 。选择依据是自然肤质与表情支持，不将候选描述成已保证去油腻。保留半写实国风，不强行增加真人毛孔、手持镜头或改脸。

创建或更新项目时，Agent检测当前节点schema、模型文件与显卡，自主构建同一份main UI/API：基础H3→原加速LoRA→公共自然肤质LoRA及惰性旁路→可选武戏动作LoRA及惰性旁路→原注意力/采样/SelfLift＋H3 latent放大/解码/音视频封装。文戏仅默认开启自然肤质，武戏默认自然肤质并按动作方案开动作分支；混合场景按片段设定动作分支。不是复制某段历史Prompt、种子或素材为通用模板。关闭任一分支必须真实绕过其LoRA加载，另一分支仍可独立工作。

自动生成iworkflow/main.ui.json及main/内API、profile、分段参数、校验和必要辅助脚本；schema核对、UI/API配对、图连线及开关组合检查后才登记可运行。用户编辑需先可靠同步，原图与执行快照留存，不覆盖人工改动。公共自然肤质和动作LoRA配置均进入实际执行API及输入指纹；自然肤质开启前校验文件存在及来源SHA256，必需触发词写入H3官方描述字段并保存到独立Prompt文件，缺失则禁止提交。模型缺失先明确记录并按授权获取，不悄悄忽略默认。

下载校验、结构检查与实际渲染检查分开记录。当前0.6与4步加速、量化H3、SelfLift组合未经成片验证；生成时检查肤质、身份、固定画风、时序闪烁、表情及动作是否变弱，在原重试预算内调整强度或明确关闭并记录理由。不以模型卡支持Ref2VA代替本机组合测试。首项目/首次武戏人工检查政策不变，其他片段自动检查。已完成影片及历史片段保持原配置，不因新增默认重做；后续新场景继承默认。

## 武戏必须有动作编排

scene_type=action/mixed的动作片段必须保存action_plan，并将其编入H3官方描述字段。即使动作LoRA关闭，武打动作Prompt仍然必需；开启LoRA也不免除动作编排。action_plan至少包含：

- intent：这次交锋的目的和人物情绪，区别试探、压制、保护、脱险等动机。
- initial_state：双方位置、距离、朝向、持械手、兵器方向、重心及上一段真实结束姿势。
- beats：按时间顺序写明行为者、目标、动作方向/轨迹、对方反应、接触或未接触结果、重心转移和后续动作；一次10秒通常聚焦一个清楚的主要交锋，再留反应与收势。
- final_state：最终站位、朝向、兵器/道具所在手、攻守关系和下一段起点。
- camera：能看清动作主体、全身或关键接触的景别和机位；避免同时复杂连招、多人大混战、频繁切镜与高速绕拍。镜头轴线保持可理解，运动跟随动作而非遮盖动作。
- acceptance：本次交锋必须出现的可观察结果，例如先出招再格挡、兵器接触位置合理、受力反应方向对应、不穿身、不换手、不增肢。

将“起势→出招→闪避/格挡/接触→反应→收势”落实到正式detailed_description或integrated_multimodal_description，不增加自创H3顶层字段。具体时间和参考标签遵守h3-prompt-writing。写清哪个人物做什么，避免连续使用歧义he/she。普通动作音、兵器声和对白同步写在对应节拍；声音技术检查保留，主观试听沿用首段确认策略。

情绪与武打同步：出招前的警觉/决心、接招时的紧张、交锋后的惊讶/克制等用可见表情、视线和姿态表现；不要让严肃打斗全程微笑。不得为套武打模板更改用户故事或人物关系。

## 影视化调度与关键帧

默认目标是剧情中的交锋。不要把“左右对称站位＋始终固定全身双人镜头＋礼毕等待＋轮流出招＋回原位”作为可复用武戏模板。左右关系用于保持轴线，不等于角色必须固定在屏幕两侧。用户明确要求擂台展示、游戏式对战或仪式剑礼时按其要求。

按剧情选择斜向纵深、前后错位、闪避让线、掠身或压迫位移，让脚步、重心和空间变化承载攻守结果。镜头可以跟随或用有目的的切镜，保持攻击方向、接触和反应可读；固定机位也可以成立，但需有明确构图/动作理由。不要用快速环绕、乱切或特写隐藏兵器和脚步错误。

开场尽快进入本次动作，不机械消耗前几秒摆架势。收势体现攻防后的新距离、位置或情绪，不为了对齐尾帧返回开场姿势。一次10秒可保持一个主要交锋，但应包含预判、加速、接触、受力、恢复的节奏，而不是长时间停住剑碰画面。

action_plan增加staging：composition（构图）、depth（纵深）、footwork（脚步重心）、camera_axis（轴线）、camera_follow（摄影随动或静止理由）、end_change（结束变化）、keyframe_alignment（首尾图与动作的一致性）、dramatic_result（剧情结果）。准备时实际查看关键帧；首尾图若已锁定站桩对称构图，先重做受影响关键帧，再同步Prompt/人数/参考与工作流。LoRA强度不能替代这些设计。

输入增加checks.action_staging=passed；输出同样记录action_staging并给出真实时段和观察。必须评估位移、重心、节奏、镜头及剧情结果，不能只凭“有两个人、有剑碰”通过。接触不清、疑似穿脸/穿身或长时间停在不合理姿势时，加密查看或回放；不能确认就记pending并在预算内修复，不能用“不一定穿模”代替验收。

本规则不规定每场必须采用同一机位、连招或切镜数量；选择依据是当前叙事、人物情绪和实际可读性。

## 首场武戏人工检查

每项目第一次出现武戏时，先制作该场的第一个10秒视频作为动作试片，展示给用户检查动作因果、肢体/兵器、表情和整体效果。用户确认后，后续武戏自动检查、生成和合并，不逐场重复审批。若项目第一个视频本身就是武戏，同一次确认同时满足项目首段和首次武戏，不重复询问。

`settings.review.action_confirmation` 默认 `first_action_video`；`content_review.first_action_human_review` 保存片段key、输出路径/SHA256、答复、时间和状态，新项目为pending。无武戏的项目不触发此检查。首次武戏被重做或相关核心动作方案发生失效变化时，使对应确认失效；普通后续重试不重置确认。

这是用户对“仅项目首段人工确认”的明确补充，其他未被修改的自动检查、重试和无试听能力记录规则继续适用。第一次武戏已生成但未获确认时，不注册为有效依赖尾帧，也不在合并中绕过该确认。

## 检查与重试

输入reviews.checks单独记录action；动作计划、场景类型和LoRA配置纳入指纹。提交前核对实际模型分支、强度、Prompt动作时序和条件绑定。输出按关键时刻检查人物/兵器数量、姿态、方向、接触、受力、收势与情绪，并记录action证据。

高分空间分块可能影响跨区域动作；适用性由本机代表性片段验证，不能凭文戏成功推断武戏成功。只把经过验证的参数称为验证配置。若动作失败，先简化主要交锋、减少同时运动、明确空间关系/反应和构图，在原有重试预算内定向修正；不要无限调高LoRA强度或堆“高速、激烈”等形容词。

人工确认仅设在项目首段与首场武戏的首个10秒试片；两者同一片段时合并确认。后续动作与情绪由Agent自动检查，不逐场审批。用户未请求武戏时不为验证开关额外生成打斗素材。普通局部工作流更新不修改已经提交的快照或自动重做既有成片。
