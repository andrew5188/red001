# 内容一致性检查

在制作、继续或修改项目时使用；独立于H3提示词格式和工作流结构校验。不得仅凭格式、关键词或成功生成文件判定内容正确。

## 需求与镜头清单

在project.json.content_review中维护status、requirements、shot_plan、input_reviews和output_reviews；空值或缺失是pending，不是passed。使用现有剧本与检查记录保存证据，不为每条要求增加单独文件。

每项requirements记录id、用户要求/来源、modality（visual/audio）、适用场次/片段、可观察的通过条件。Agent提出的实施细节标明为推导，不冒充用户原话；只对影响核心创作方向的未决问题询问。禁止默认套用上个故事的视觉要求。

首次渲染前在现有完整剧本中加入中文镜头清单并向用户简要展示：片段、实际可见环境与动作、对白/声音、起止状态、对应需求ID。已确认方向且已获制作授权时继续，无需每段审批。

例如用户要求从开场呈现雪景，可在适用镜头规定屋檐/栏杆可见积雪、前中景有飘雪；“角色说今日请你看雪”不能代替这些画面。雪仅是示例，不是全项目默认；也不要强制所有特写都露出整座山或整个场景。

## 输入审查：准备和提交都检查

逐段检查以下内容，记录每项pass/fail/pending及具体依据：
1. 剧本与镜头清单符合该段需求，剧情因果没有擅自推迟或取消必需画面。
2. 查看真实人物和场景参考图，而非根据文件名推测。参考中的天气、服装、时间等与镜头兼容。
3. 读取完整H3 Prompt，核对画面描述、保留要求、负面约束与对白；识别“无雪/保留裸地”等与需求冲突的描述，不能仅搜索是否出现“雪”。
4. 按emotion-direction.md核对本场主情绪、人物不同反应、每段表演变化和可见构图；在input_reviews.checks中记录performance，并将本场/本段performance_plan纳入指纹。
5. 武戏按action-direction.md检查动作编排及LoRA开关；记录action检查，把场景类型、action_plan及实际动作LoRA配置纳入指纹。
6. 核对绑定后的实际API：使用的是正确版本Prompt、参考槽位、上传文件与连续性条件。磁盘Prompt正确但执行快照仍旧，仍判fail。

每段input_reviews记录status、逐项结论、证据、检查时间及覆盖文件的SHA256，至少覆盖剧本/镜头清单、需求快照、Prompt、实际参考源文件、分段配置、UI/API/配置和适用的引导文件。上传名另记录与本地源的映射。不能虚构未查看图片的视觉结论。脚本只能验证记录状态与指纹，语义审查仍由Agent实际执行。

任一必要项fail/pending、依赖stale或文件指纹变化，禁止提交。准备后编辑输入需重新审查并重新准备；不直接篡改历史执行快照。下一段可在前段渲染时起草文字，但不能提前提交依赖前段的生成。

## 输出审查：首段人工确认，后续自动检查

分开记录：
- technical：可解码、尺寸、时长、帧率和音轨参数。
- visual：逐项核对本段需求ID；查看开头、中段、结尾及关键动作时刻。对持续天气或动态动作，检查相关时间段，单张静帧不能证明全段持续成立。保存实际帧路径、时间码与观察。
- performance：按本段情绪节拍记录实际表情、视线和反应的时间码，判断叙事情绪是否可读、变化自然、承接前段；未检查不视为通过。
- action：武戏检查出招、反应、方向、接触结果、收势和兵器/肢体一致性；动作LoRA启用不等于动作检查通过。
- audio：实际试听或使用可用分析能力核对对白、说话人、必要环境声/音效/音乐；转写只能作为对白证据，音轨存在、响度和转写均不能独自证明音乐或完整听感合格。
- continuity：前后站位、动作、道具、场景状态和声音衔接。

每段output_reviews记录实际产物路径/指纹、逐项结果、证据和未验证项。项目首个视频须展示给用户人工检查，确认绑定实际输出指纹；未确认前不推进后段。 首次武戏另按action-direction.md检查首个动作试片，若与项目首段相同则复用同一确认；无武戏不触发。后续视频不请求人工确认，由Agent自动核对技术、画面与衔接。有可用音频能力则使用；没有时记audio=waived、主观质量=未验证、来源=首段确认后的自动继续策略，保留技术音频检查并继续制作。必要技术/画面/衔接项缺失仍是pending，实际错误按预算修复，不能以策略豁免掩盖已知失败。

只有必要自动检查通过、首段人工确认有效、输入/输出版本未变化时才标complete并登记有效衔接；后续audio允许按已登记策略waived，不等于听感通过。最终合并采用同一策略，检查顺序、核心画面、完整音轨和技术参数后自动交付，不新增人工验收关卡，不沿用旧final_output冒充新成果。

## 对白、动作与交付接受分开记录

有对白按[dialogue-direction.md](dialogue-direction.md)逐句计划和核对声音/口型归属；武戏按action-direction.md核查影视化调度。新输入与输出使用quality_policy_version=1，实际执行接入scripts/quality_gates.py；脚本验证资料和拦截状态，不负责自动判断口型、动作自然度或证明画质。

在输出依赖与合并入口再次拦截未解决的用户问题，不能只在生成入口检查。候选问题尚未精确定位时记录candidate_segments/outputs并待复查，不能编造秒点或宣布所有候选都发生错误。返修保留尝试次数和旧证据；变更计划/关键帧后重新审查输入，不增加内容版本号绕过重试预算。

“继续”“合并做好的视频”是执行或交付授权，不是用户逐项验证过声音、动作物理关系的证据。用户明确接受已披露偏差的版本时可按其范围导出，但另存delivery_acceptance和限制；未验证项仍为未验证、已知错误仍为错误，不把checks改成passed来满足脚本。一般成片通过检查不需新增确认；只有原有首段/首场武戏关卡保留。普通交付授权不自动将质量不合格的片段注册为后续连续性依据。

新反馈优先于旧接受记录。用户拒绝某片后使相关输出/合成与适用首场确认失效；不能凭先前合并授权恢复passed。音频waived只表示能力限制下的已授权继续，绝不覆盖已知重复说话、错误角色口型或其他明确缺陷。

更新规则不重写历史检查为“当时已执行”。未受影响的历史合格片段保留其记录；新生成/返修必须使用新计划与检查。

## 修改与失效传播

用户更改要求，或剧本、参考图、Prompt、绑定配置被编辑后，按实际依赖重新评估：
- 受影响input_reviews/output_reviews标stale并记录原因，更新项目内容状态；首段文件或其核心要求失效时，同时使first_video_human_review失效。
- 已准备的执行快照不可再提交；历史运行状态success仅表示任务执行成功。
- 受影响视频及其尾帧停止作为有效下游输入；移出可用引导登记，保留历史文件与来源。
- 沿连续性/素材依赖传播，重新检查受影响合成；无关人物素材和独立片段不必重做。
- 查询任务、收集文件、重新启动服务均不能清除stale。只有修正对应输入并实际重新审查才能恢复。
- 新规则迁入旧项目时补充待审记录，不能把旧complete直接转换成新规则passed。

单纯更新Agent或讨论原因，不重写剧情、不生图、不启动或恢复渲染。

## 出镜计划与人数验收

在场景保存允许人物清单，在片段cast_plan保存可执行镜头安排。至少含：allowed_characters（角色ID）、offscreen_characters、passersby_count、bit_players_count、max_simultaneous_people、shots及status。路人和龙套为0也必须显式记录；非0时另列稳定ID/外貌、站位、行为和入退场，不用“若干人”替代可验收安排。群体规模确实可浮动时写明批准范围。

shots按时间段列出allowed_characters、required_characters、visible_count_min/max及入画/离画事件，覆盖整段；段落可代表镜头内部人数变化。切镜/特写只要求该镜头的必见人物，遮挡保留身份轨迹，不能把场内人数当作每帧固定人数。整段独立人物数与同时可见人数分开。普通影子/正常倒影不算新角色，但未安排的人脸/人形、克隆实体以及未经剧情允许的分身都应核查。

输入cast检查：剧本和逐镜头人数一致，画外人物不进入当前镜头人物参考，逐个核对实际人物图、无人环境图和引导帧是否携带其他人物。三视图误解时派生单人参考；仍失败可在现有预算内使用经检查的单人构图首帧，必须真实接入节点。将人数/身份/站位写进H3既有正式描述字段，不能新增cast_plan等官方Prompt顶层字段。执行快照包含cast_plan指纹；计划改变后旧输入审查失效。

输出cast检查：记录预期和观察到的人数/身份、时间码及异常位置，检查开头、中间、结尾与每次切镜、入画/离画、遮挡重现；发现可疑处加密帧或逐帧查看。前中后景、边缘、远处人影、额外手脚也需检查。抽帧只能证明所查看样本，不能写成逐帧全片已查。任何明确多余/重复人物或缺失必见人物判failed，保留失败证据并禁止作尾帧和合并素材。技术成功不覆盖cast失败。无变化的既有合格成片不因加入本规则自动重做；新片段缺失或draft计划不提交，历史运行快照不补写成事前已审。

## 大量群演：先构建关键场景图

当镜头出现大量群演、集市/观众/队列等成组人群，或复杂交错进出场时，在视频前使用图片生成工具构建含人物的关键场景图。先在cast_plan明确crowd_required、人数、分组和站位，再把当前有效主角参考与无人场景组合成计划中的画面，不能只用文字要求视频自行安排人群。不对所有项目硬设相同人数阈值；按画面密度、遮挡和运动复杂度判定，显然的大规模人群不得标不适用。

关键图检查主角身份和辨识度、群演总数/各组人数、前中后景站位、服装分组、朝向、主角通道及出入口。可逐一辨认的前中景人物使用明确数量；极远景密集人群若无法数清，应记录规模和分区/范围，明确“精确人数未验证”，不能伪称精确计数通过。减少遮挡或拆镜以满足需要精确计数的镜头。

把已检查关键图保存到03_分场制作/<场次>/关键帧/，记录来源图、时间用途、SHA256、cast_plan和检查状态。复杂入场、站位变化或交锋按需要增加关键帧；它们是不同时间的画面，不能当作同时存在的多个场景。按实际H3模式及节点能力绑定首帧/关键帧/参考；不支持多关键帧时拆成可控镜头或选择已验证模式，不能虚构节点。

含人关键帧不放进无人场景库。提交前核对实际API确实绑定已检查图片及正确时间，不能仅把图保存在目录。crowd_required为true而关键图缺失、指纹变化、检查未通过或未实际绑定时拦截。成片仍检查意外人物、主角被复制、人群穿模和进出场；关键图降低不确定性，不保证人数一次生成正确。

## 全部视频登记与按编号返修

使用本skill的scripts/video_registry.py --workspace <工作区绝对路径>生成根目录视频登记.md，以及各项目iworkflow/main/video_registry.json。登记覆盖当前视频、历史/失败尝试、已提交但尚无视频的任务、候选与正式合并成片；磁盘扫描补充未匹配文件，不能把它们默认判为已验收。待制作片段另外列状态，不伪造输出文件。

每条记录包含稳定编号、项目、场次/片段、版本/尝试、实际任务ID、视频路径、时长/尺寸、指纹、执行与内容验收状态、问题、检查证据及实际工作流。执行成功和内容通过分开。编号不随列表排序重排；历史记录及文件保留。片段以项目ID+场次+片段+内容版本+尝试编号标识；成片或未匹配文件以持久登记标识，移动文件后核对指纹并保留原编号。

项目初始化/恢复、提交、归档、验收、失败、用户反馈、返修和合并后刷新登记。项目执行脚本把刷新接入状态保存；其他项目没有该钩子时由Agent在状态更新后调用。登记从清单和实物导出，不是第二个手工进度来源；不得手改导出的表格冒充验收。刷新失败应报告，不声称已完成登记。

用户可说“重做编号X，3–5秒多了一个人”。先按编号定位精确文件和尝试，在project.json的video_issues记录issue_id、record_id/output、时间码、原始反馈、状态和处置。未指明视频的角色级问题可以按affected_characters登记范围，不擅自编造时间码。将受影响结果/审查标待修复或stale；已知错误不再被当作有效衔接或合成输入。返修生成新尝试，记录关联，成功复核后再切换有效输出；检查依赖尾帧和最终合成，只重做受影响部分。沿用已有重试预算；超限先报告，不能更改版本号绕过预算。登记可播放链接用于用户定位，不额外增加逐片人工批准。
